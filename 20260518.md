Aula prática usando o **Killercoda** (laboratório Docker no navegador). Cada aluno terá seu próprio ambiente isolado, então **não precisamos mais usar prefixos com nome** nos recursos como fizemos no servidor compartilhado.

### Testando acesso a um site no contêiner

Sempre que subirmos um contêiner com porta publicada (`-p`), temos duas formas de testar:

* **No terminal do Killercoda:**

```bash
curl localhost:80

```

* **No navegador:** clique no botão **"Traffic Port Accessor"** no topo da página, digite a porta (ex: `80`) e abra a URL gerada — equivalente a abrir o site numa aba nova.

## 🏗️ Arquitetura da plataforma de contêineres

Quando você executa `docker run nginx`, o comando passa pela seguinte cadeia:

```
docker (CLI)  →  dockerd (daemon)  →  containerd  →  runc  →  contêiner
```

* **docker (CLI):** o cliente que você usa no terminal; envia comandos via API REST
* **dockerd:** o daemon que gerencia imagens, contêineres, redes e volumes
* **containerd:** runtime de alto nível responsável pelo ciclo de vida do contêiner
* **runc:** runtime de baixo nível que cria o processo isolado usando recursos do kernel Linux (namespaces e cgroups)

### Contêiner vs Máquina Virtual

|                | Contêiner                       | Máquina Virtual         |
| -------------- | ------------------------------- | ----------------------- |
| Kernel         | compartilhado com o host        | próprio (dentro da VM)  |
| Inicialização  | segundos                        | minutos                 |
| Tamanho típico | MB                              | GB                      |
| Isolamento     | processo + namespaces + cgroups | hardware virtualizado   |

Um contêiner é, no fundo, um **processo do Linux isolado** — não é uma "máquina pequena".

## 📦 Imagens vs Contêineres

* **Imagem:** template somente-leitura armazenado no disco (ex: `nginx`, `alpine`, `ubuntu`)
* **Contêiner:** instância em execução de uma imagem; podemos ter vários contêineres rodando a partir da mesma imagem

> Analogia: imagem é a **classe**, contêiner é o **objeto** (instância dela).

```bash
# Listar imagens locais
docker images

# Listar contêineres em execução
docker ps

# Listar TODOS os contêineres (inclusive os parados)
docker ps -a

```

### Imagens públicas — Docker Hub

O **Docker Hub** (https://hub.docker.com) é o repositório público padrão de imagens. Quando você roda `docker run nginx`, o Docker baixa a imagem `nginx:latest` de lá se não tiver localmente.

```bash
# Baixar uma imagem sem executar
docker pull alpine

# Buscar imagens no registry
docker search redis

```

## 🛠️ Mão na Massa

### Passo 1: Execução simples (Foreground)

```bash
docker run --name nginx-1 nginx

```

* O terminal fica preso ao processo do contêiner
* 👉 **Teste:** aperte `Ctrl + C` para parar — como o terminal estava amarrado ao processo, o contêiner para de rodar

### Passo 2: Rodando em background

A flag `-d` (detach) executa o contêiner em segundo plano e libera o terminal.

```bash
docker run -d --name nginx-2 nginx

```

* 👉 **Verifique:**

```bash
docker ps

```

### Passo 3: Publicando a porta

O nginx escuta na porta `80` **dentro do contêiner**. Para acessar de fora, precisamos publicar essa porta no host com `-p <host>:<contêiner>`.

```bash
docker run -d --name web -p 80:80 nginx

```

* 👉 **Teste no terminal:**

```bash
curl localhost:80

```

* 👉 **Teste no navegador:** clique em **Traffic Port Accessor** → digite `80` → veja a página de boas-vindas do nginx

### Passo 4: Entrando no contêiner (exec)

Vamos alterar o conteúdo da página inicial.

```bash
docker exec -it web bash

```

Dentro do contêiner:

```bash
echo "<h1>Meu primeiro container Docker!</h1>" > /usr/share/nginx/html/index.html
exit

```

* 👉 **Verifique:** `curl localhost:80` (e recarregue a aba do Traffic Port)

### Passo 5: Persistência com volumes

Se removermos o contêiner, a alteração feita acima se perde. Para preservar dados, montamos uma pasta do host dentro do contêiner.

```bash
# Cria a pasta no host com um arquivo HTML
mkdir -p /tmp/site
echo "<h1>Site persistente</h1>" > /tmp/site/index.html

# Remove o contêiner anterior (libera o nome e a porta)
docker rm -f web

# Sobe um novo contêiner montando o volume
docker run -d --name web -p 80:80 -v /tmp/site:/usr/share/nginx/html nginx

```

* 👉 **Teste:** `curl localhost:80`
* 👉 **Reflexão:** mesmo se destruirmos o contêiner e recriarmos, o arquivo em `/tmp/site/index.html` continua no disco do host.

### Passo 6: Redes — comunicação entre contêineres

Por padrão, os contêineres ficam na rede `bridge`. A boa prática é criar uma rede própria por aplicação — nela o Docker resolve o **nome** do contêiner como hostname.

1. Crie uma rede:

```bash
docker network create minha-rede

```

2. Suba um nginx nessa rede:

```bash
docker run -d --name site-privado --net minha-rede nginx

```

3. Suba um alpine na mesma rede para testar a comunicação:

```bash
docker run -it --name terminal --net minha-rede alpine sh

```

4. Dentro do alpine:

```bash
# Instala o curl
apk add --no-cache curl

# Acessa o nginx pelo NOME do contêiner
curl site-privado

```

* 👉 **Observação:** na rede `bridge` padrão isso não funcionaria — a resolução por nome só existe em redes customizadas.

## 🎯 Desafio

Suba um contêiner do **httpd** (Apache, outra imagem pública) servindo uma página customizada via volume, em uma rede própria, publicado em uma porta diferente da do nginx (ex: `8080`). Acesse pelo Traffic Port.

Dicas:

* `docker run` com `-d --name`, `-p 8080:80`, `-v` e `--net`
* a raiz do Apache na imagem oficial é `/usr/local/apache2/htdocs/`

## 🧹 Limpeza

No Killercoda a sessão expira automaticamente, mas vale praticar a higiene:

```bash
docker rm -f nginx-1 nginx-2 web site-privado terminal
docker network rm minha-rede

```

Para apagar tudo de uma vez (cuidado em ambientes reais):

```bash
docker rm -f $(docker ps -aq)

```
