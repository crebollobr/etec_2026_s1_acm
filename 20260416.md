## 1. A Árvore de Diretórios do Linux (FHS)
No Linux, tudo começa na raiz (`/`). Diferente do Windows (que usa `C:\`, `D:\`), o Linux monta todos os discos e dispositivos dentro de uma única grande árvore de diretórios. Vamos explorar **todas** as pastas principais do sistema:

* `/bin` (Binaries): Contém os comandos binários essenciais executáveis por todos os usuários (ex: `ls`, `cp`, `cat`).
* `/boot`: Arquivos essenciais para a inicialização do sistema (boot), como o Kernel do Linux (`vmlinuz`) e o gerenciador de boot (GRUB).
* `/dev` (Devices): Arquivos de dispositivos. No Linux, "tudo é arquivo", incluindo hardware (discos rígidos como `/dev/sda`, terminais, etc).
* `/etc`: **O coração das configurações.** Contém todos os arquivos de configuração do sistema e dos serviços. *(Aprofundaremos nesta pasta a seguir)*.
* `/home`: Diretórios pessoais dos usuários comuns (ex: `/home/joao`, `/home/maria`).
* `/lib`, `/lib32`, `/lib64`: Bibliotecas compartilhadas essenciais (equivalentes às DLLs do Windows) necessárias para os binários em `/bin` e `/sbin`.
* `/media`: Ponto de montagem temporário e automático para mídias removíveis (pendrives, CDs).
* `/mnt` (Mount): Ponto de montagem temporário para uso manual pelo administrador (ex: montar um disco de rede).
* `/opt` (Optional): Usado para a instalação de pacotes de software adicionais/terceiros que não fazem parte do repositório padrão.
* `/proc` (Processes): Um sistema de arquivos virtual. Ele não existe no disco real, apenas na RAM. Contém informações sobre processos em execução e sobre o kernel/hardware.
* `/root`: O diretório "home" do superusuário (o administrador `root`). Não confunda com a raiz `/`.
* `/run`: Dados voláteis de tempo de execução (runtime). Substitui antigas funções do `/var/run`. Arquivos aqui são limpos a cada reinicialização.
* `/sbin` (System Binaries): Binários essenciais do sistema, geralmente comandos exclusivos para administração (necessitam de `sudo` ou `root`).
* `/srv` (Services): Dados específicos de serviços rodando no sistema (ex: arquivos de um servidor web ou FTP).
* `/sys`: Outro sistema de arquivos virtual (como o `/proc`), usado para interagir de forma mais estruturada com o kernel e o hardware (hotplug, gerenciamento de energia).
* `/tmp` (Temporary): Arquivos temporários criados por programas. Geralmente é limpo no boot.
* `/usr` (Unix System Resources): A segunda hierarquia mais importante. Contém a maioria dos programas de usuários, bibliotecas e documentação (`/usr/bin`, `/usr/share`).
* `/var` (Variable): Dados que crescem e mudam constantemente, como arquivos de log (`/var/log`), bancos de dados, spools de impressão e e-mails.

## 2. Mergulhando no diretório `/etc` e o Gerenciamento de Usuários

O diretório `/etc` guarda as configurações do sistema operacional. **A regra de ouro aqui é: tudo é arquivo de texto puro.** Você não precisa de ferramentas especiais ou registros complexos (como o Regedit do Windows) para alterar o sistema; basta um editor de texto como o `nano` ou `vim`.

### 2.1. O arquivo `/etc/passwd` (O "Banco de Dados" de Usuários)
Historicamente, o arquivo `/etc/passwd` guardava os usuários e suas senhas. Hoje, ele atua como um banco de dados local que lista os usuários, mas **não contém mais a senha**.

```text
# Exemplo de uma linha no /etc/passwd visualizada pelo professor
joao:x:1000:1000:Joao da Silva,,,:/home/joao:/bin/bash
```
*Observe o `x` no segundo campo.* Ele indica que a senha não está ali, mas sim "escondida" (shadowed).

> **Nota:** O `/etc/passwd` é apenas um banco de dados local de usuários. Em ambientes corporativos maiores, o Linux pode ser configurado para buscar usuários em outros bancos de dados de rede, como **LDAP** ou **NIS** (Active Directory).

### 2.2. O arquivo `/etc/shadow` e a Criptografia (Hashes)
A senha real foi movida para o `/etc/shadow` por uma questão de segurança básica: o `/etc/passwd` precisa ser lido por qualquer usuário (para saber quem é dono de qual arquivo), mas o `/etc/shadow` **só pode ser lido pelo `root`**.

```text
# O professor exibe o arquivo (requer sudo/root)
sudo cat /etc/shadow | grep joao
joao:$6$rxyz83...$ABcDeFgHiJkLmNoPqRsTuVwXyZ0123456789:19000:0:99999:7:::
```

**Segurança da Senha e Criptografia:**
* A string gigantesca `$6$...` não é a senha em texto claro, mas sim um **Hash** (neste caso, SHA-512, indicado pelo `$6$`).
* **Hash é uma via de mão única (One-Way):** A criptografia transforma a senha "123456" naquele código gigantesco. Não existe um "modo fácil" de pegar aquele hash e reverter para "123456". 
* Quando o usuário digita a senha no login, o sistema calcula o hash do que foi digitado e compara com o hash salvo no `/etc/shadow`. Se bater, o acesso é liberado.

## 3. A Mágica da Autenticação: PAM (Pluggable Authentication Modules)

Como o sistema sabe se deve checar a senha no `/etc/shadow` ou buscar em um servidor remoto LDAP? A resposta é o **PAM**.

O PAM é um intermediário poderoso. Quando um programa precisa autenticar alguém, ele não programa isso do zero; ele "pede" ao PAM. 

* O PAM é altamente configurável. Você pode dizer a ele: "Para autenticar, verifique primeiro o banco local (`/etc/passwd` + `shadow`). Se não achar, tente no LDAP. Ou tente em ambos".
* **Arquivos do PAM:** Ficam na pasta `/etc/pam.d/`. Dentro dessa pasta, há um arquivo de configuração para cada serviço.
    * Exemplos: `/etc/pam.d/su`, `/etc/pam.d/sudo`, `/etc/pam.d/sshd`.
    * Nesses arquivos, módulos específicos (como `pam_unix.so` para arquivos locais ou `pam_ldap.so` para LDAP) são invocados.

### 3.1. SSH e PAM
O **SSH** (Secure Shell) é a ferramenta padrão para acesso remoto no Linux. O serviço do SSH (`sshd`) não verifica senhas por conta própria. Ele repassa essa tarefa ao PAM. Portanto, o SSH pode perfeitamente usar o banco de dados local ou o LDAP, dependendo unicamente de como o PAM do servidor está configurado.

## 4. O Conceito de AAA (Authentication, Authorization, Accounting)

Toda a gestão de segurança e acesso discutida até aqui faz parte de um framework de segurança clássico chamado **AAA**.

### A - Authentication (Autenticação)
**"Quem é você?"**
É o ato de provar sua identidade. No nosso cenário, a autenticação é feita pelo **PAM**, verificando a senha que o usuário digitou contra o banco de dados (seja ele o arquivo `/etc/shadow` local ou um servidor LDAP remoto).

### A - Authorization (Autorização)
**"O que você tem permissão para fazer?"**
Depois que o PAM diz "Ok, você é o João", a Autorização entra em cena.
* **Exemplo via SSH:** O servidor SSH verifica o arquivo `/etc/ssh/sshd_config`. É muito comum administradores configurarem `PermitRootLogin no`. Isso significa: mesmo que a senha esteja correta, o root *não está autorizado* a logar diretamente via rede. Outra limitação comum é a diretiva `AllowUsers joao maria`, garantindo que apenas eles tenham acesso.
* **Exemplo via Sistema de Arquivos:** As permissões dos arquivos. Como vimos, um usuário comum não está autorizado a ler o `/etc/shadow`. Ele tentará ler, mas receberá um "Permission denied" (Permissão negada) baseado nas permissões de leitura do arquivo.

### A - Accounting (Auditoria / Contabilização)
**"O que você fez enquanto esteve aqui?"**
É o rastreamento das ações. Embora não seja o foco principal desta aula, vale mencionar que o Linux registra quem logou e o que fez. (Ex: logs em `/var/log/auth.log` registram todos os sucessos e falhas do PAM e do SSH).

## 5. Modernizando a Autenticação: O papel do SSSD (System Security Services Daemon)

Para fechar o tema de autenticação em rede, é essencial entendermos a evolução desse processo. Antigamente, para integrar o Linux a um diretório remoto, o sistema e o PAM usavam módulos diretos (como `pam_ldap` ou clientes nativos do NIS). Hoje, o padrão moderno e seguro na maioria das distribuições é o **SSSD**.

O SSSD atua como um intermediário inteligente (um daemon/serviço) entre o sistema operacional local e os provedores de identidade remotos.

* **Relação com o LDAP e NIS:** O SSSD substitui as antigas integrações diretas. Em vez de o servidor Linux interrogar o servidor LDAP ou NIS a cada segundo (por exemplo, toda vez que alguém roda um `ls -l` para saber o nome do dono de um arquivo), o sistema pergunta ao SSSD. O SSSD, por sua vez, é quem centraliza e gerencia a comunicação real com os servidores LDAP, NIS, FreeIPA ou até mesmo Active Directory (Windows).
* **Relação com a Autenticação (PAM):** Quando SSSD está em uso, os arquivos do PAM (em `/etc/pam.d/`) são configurados para chamar o módulo do SSSD (geralmente `pam_sssd.so`). Quando o usuário digita a senha no SSH, o PAM aciona o SSSD, que valida a credencial com o servidor remoto (como o LDAP) e devolve a resposta (sucesso ou falha) para o PAM.
* **A Grande Vantagem: Cache Offline:** O principal motivo de o SSSD ter se tornado o padrão é a sua capacidade de fazer cache (guardar uma cópia temporária e criptografada) dos usuários, grupos e credenciais. Se o servidor LDAP/NIS ficar fora do ar ou o servidor Linux perder a conexão de rede, os usuários que já se autenticaram recentemente **continuarão conseguindo fazer login** e trabalhar normalmente usando o cache local do SSSD. Nas configurações antigas (sem SSSD), uma queda de rede significava que ninguém mais conseguiria logar no servidor.


```
[sssd]
services = nss, pam
config_file_version = 2
domains = empresa.local

[domain/empresa.local]
id_provider = ldap
auth_provider = ldap
chpass_provider = ldap

# Servidor LDAP
ldap_uri = ldap://ldap.empresa.local

# Base de busca
ldap_search_base = dc=empresa,dc=local

# Bind (usuário técnico)
ldap_default_bind_dn = cn=bind,dc=empresa,dc=local
ldap_default_authtok = senha123

# Estrutura dos usuários
ldap_user_search_base = ou=usuarios,dc=empresa,dc=local
ldap_group_search_base = ou=grupos,dc=empresa,dc=local

# Atributos comuns (OpenLDAP padrão)
ldap_user_object_class = inetOrgPerson
ldap_user_name = uid
ldap_user_uid_number = uidNumber
ldap_user_gid_number = gidNumber
ldap_user_home_directory = homeDirectory
ldap_user_shell = loginShell

# Cache (importante)
cache_credentials = true
enumerate = false

# TLS (recomendado)
ldap_id_use_start_tls = true
ldap_tls_reqcert = demand
ldap_tls_cacert = /etc/ssl/certs/ca-certificates.crt
```
