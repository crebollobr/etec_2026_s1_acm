# ☸️ Kubernetes — Aula 03: Proxy Reverso com Ingress (a Porta de Entrada do Cluster)

Na aula passada, declaramos todo o nosso ambiente em YAML (Deployment + Service) e deixamos a aplicação em rede interna — mas o acesso do navegador ainda dependia de um túnel manual de teste (`port-forward`), que prende o terminal e morre junto com a sessão.

Hoje instalamos a **porta de entrada oficial** do cluster: um **proxy reverso**, que no mundo Kubernetes atende pelo nome de **Ingress**.

---

## 🧠 Teoria: O que é um Proxy Reverso?

A palavra *proxy* significa "procurador, intermediário" — alguém que age em seu nome.

* Um **proxy comum** (forward proxy) fica na frente dos **clientes**: você navega e ele sai na internet por você (empresas usam para filtrar/registrar a navegação dos funcionários).
* Um **proxy reverso** fica na frente dos **servidores**: o visitante acha que está falando com o site, mas na verdade fala com o porteiro — e o porteiro repassa a conversa para o servidor de verdade, escondido lá atrás.

Por que toda empresa séria usa um? Porque o porteiro é o **ponto único de entrada**, e nele você concentra:

* 🔒 **Segurança** — é nele que se instala o **certificado SSL** (o cadeado do HTTPS), regras de **firewall** de aplicação (bloquear IPs, limitar requisições por segundo, filtrar ataques). Os servidores de verdade ficam **invisíveis**, em rede interna, inalcançáveis de fora.
* 🪢 **Balanceamento de carga** — um porteiro pode distribuir os visitantes entre vários servidores (vamos explorar isso na Aula 04).
* 🚪 **Roteamento** — `loja.empresa.com` vai para um servidor, `blog.empresa.com` vai para outro, e todos entram pela mesma porta.
* ⚡ **Cache** — o porteiro pode guardar respostas prontas e responder sem incomodar o servidor.

### E no Kubernetes? O Ingress

No Kubernetes, o proxy reverso é um cidadão de primeira classe, dividido em duas peças:

* **Ingress Controller** → o porteiro **de verdade**: um proxy reverso rodando como Pods, gerenciado pelo próprio cluster. O mais usado do mundo é feito com **nginx** — sim, o mesmo programa que serve nossas páginas é também o proxy reverso mais famoso da internet.
* **Ingress (o recurso)** → as **ordens do porteiro**: um arquivo YAML com as regras de roteamento ("quem pedir X, entregue ao serviço Y"). Ou seja: até a configuração do proxy vira **Infraestrutura como Código**.

O MicroK8s traz o Ingress Controller pronto como um *addon* — um comando e ele está contratado.

> 🔒 **Sobre o pilar Segurança da nossa tabela:** nesta aula montamos a **arquitetura** que permite segurança (ponto único de entrada + aplicação escondida em rede interna). Não vamos configurar SSL nem firewall — mas, ao final, você vai saber exatamente **onde** eles entrariam.

## 🏗️ 1. Etapa 1 — O Site Escondido (rede interna)

Primeiro, o site — o mesmo Deployment + Service da aula passada, recriado do zero em instantes (viva a Infraestrutura como Código).

Crie a pasta do projeto e o conteúdo:

```bash
mkdir -p /root/projeto-ingress && cd /root/projeto-ingress
mkdir -p /srv/www

```

Salve o conteúdo abaixo como `/srv/www/index.html`:

```html
<h1>🏠 Site interno</h1>
<p>Voce so consegue me ver porque passou pelo porteiro (Ingress).</p>
```

Salve o conteúdo abaixo como `site-deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: meu-site
spec:
  replicas: 1
  selector:
    matchLabels:
      app: meu-site
  template:
    metadata:
      labels:
        app: meu-site
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80
        volumeMounts:
        - name: conteudo
          mountPath: /usr/share/nginx/html
      volumes:
      - name: conteudo
        hostPath:
          path: /srv/www
```

Salve o conteúdo abaixo como `site-service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: site-interno
spec:
  type: ClusterIP
  selector:
    app: meu-site
  ports:
  - port: 80
    targetPort: 80
```

* `type: ClusterIP` → como vimos na Aula 02: endereço fixo **interno**. De fora, ninguém alcança.
* `metadata.name: site-interno` → guarde esse nome. Ele será o "endereço" que o porteiro vai usar.

Aplique e confira:

```bash
kubectl apply -f site-deployment.yaml -f site-service.yaml
kubectl get pods
kubectl get services

```

Agora a constatação importante. Teste a porta 80 **da máquina**:

```bash
curl localhost

```

`Connection refused` — **ninguém** está atendendo na porta 80 do computador. O site está vivo (está `Running`!), mas em rede interna, invisível para a rua. Exatamente como manda a boa arquitetura.

### 📡 Como o porteiro vai encontrá-lo? O DNS interno

O Kubernetes tem um **DNS interno**: todo Service ganha automaticamente um **nome de domínio dentro do cluster**. Prove com um Pod descartável (`--rm` apaga o Pod ao sair, `-it` abre um terminal dentro dele):

```bash
kubectl run teste --rm -it --image=busybox -- sh

```

Dentro do Pod, chame o site **pelo nome do Service**:

```bash
wget -qO- http://site-interno

```

O HTML da nossa página aparece! Saia com `exit`. É assim que os componentes se acham no Kubernetes: IPs mudam o tempo todo, mas **nomes de Services são estáveis**. O porteiro vai usar exatamente esse nome.

## 🚪 2. Etapa 2 — Contratando o Porteiro (Ingress Controller)

Hora de ligar o addon do MicroK8s:

```bash
microk8s enable ingress

```

O que esse comando fez? Instalou o **nginx Ingress Controller**: Pods rodando um nginx configurado para ser proxy reverso, gerenciados pelo próprio cluster. Veja-os nascer (eles moram em um *namespace* separado — pense em namespaces como "pastas" que organizam os objetos do cluster; `-n` escolhe a pasta):

```bash
kubectl get pods -n ingress

```

Rode de novo até o pod `nginx-ingress-microk8s-controller-...` ficar `Running`.

E aqui está o detalhe perfeito para o nosso laboratório: o porteiro já nasce **escutando nas portas 80 e 443 da máquina** — sem portas esquisitas, sem IP extra. Prove:

```bash
curl localhost

```

Mudou! Em vez de `Connection refused`, agora veio um **`404 Not Found` assinado pelo nginx**. Leia a cena: o porteiro está na portaria atendendo (porta 80 ocupada!), mas ainda **não recebeu nenhuma ordem** — então responde "não conheço esse endereço" para todo mundo.

## 📜 3. Etapa 3 — As Ordens do Porteiro (o recurso Ingress)

As regras de roteamento são declaradas em YAML, como tudo no Kubernetes. Salve o conteúdo abaixo como `ingress.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: entrada-site
spec:
  ingressClassName: public
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: site-interno
            port:
              number: 80
```

Dissecando:

* `apiVersion: networking.k8s.io/v1` → Ingress mora no departamento de rede da API.
* `kind: Ingress` → o tipo de objeto: um conjunto de regras de roteamento.
* `ingressClassName: public` → **para qual porteiro** é esta ordem (um cluster pode ter vários controllers). No MicroK8s, o porteiro registrado chama-se `public` — confira com `kubectl get ingressclass`.
* `rules` → a lista de ordens. A nossa: para requisições HTTP cujo caminho comece com `/` (ou seja, **todas**)...
* `backend.service` → "...entregue ao Service `site-interno`, na porta 80". Repare: é o **nome** do Service — o porteiro o encontra pelo DNS interno que acabamos de testar!

Aplique e confira:

```bash
kubectl apply -f ingress.yaml
kubectl get ingress

```

E o grande momento:

```bash
curl localhost

```

**Nossa página!** Agora abra no navegador: menu (☰) → **Traffic Ports** → botão **80**. O site está no ar pela porta oficial, sem nenhum túnel manual, sem nenhum terminal preso. 🎉

O caminho completo de cada requisição:

```
Navegador
   → porta 80 da máquina (Ingress Controller / nginx porteiro)
      → regra do Ingress "entrada-site"
         → DNS interno resolve "site-interno"
            → Service site-interno (ClusterIP)
               → Pod meu-site (nginx com nossa página)
```

## 🏘️ 4. Etapa 4 — O Superpoder do Roteamento (vários sites, uma porta)

Lembra da pergunta teórica: "como `loja.empresa.com` e `blog.empresa.com` moram no mesmo servidor?" Resposta: o proxy reverso lê o **nome do site** que o navegador pede (o cabeçalho `Host`) e roteia cada nome para um serviço diferente. Tudo **pela mesma porta 80**.

Vamos provar subindo um segundo site — para variar, com o **Apache** (`httpd`), outro servidor web famoso, cuja página padrão diz "It works!".

Salve o conteúdo abaixo como `admin-deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: site-admin
spec:
  replicas: 1
  selector:
    matchLabels:
      app: site-admin
  template:
    metadata:
      labels:
        app: site-admin
    spec:
      containers:
      - name: apache
        image: httpd
        ports:
        - containerPort: 80
```

Salve o conteúdo abaixo como `admin-service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: admin-interno
spec:
  type: ClusterIP
  selector:
    app: site-admin
  ports:
  - port: 80
    targetPort: 80
```

E a nova ordem para o porteiro — agora com `host`. Salve o conteúdo abaixo como `admin-ingress.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: entrada-admin
spec:
  ingressClassName: public
  rules:
  - host: admin.meusite.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: admin-interno
            port:
              number: 80
```

* `host: admin.meusite.com` → esta regra só vale para quem pedir **esse nome**. A regra da Etapa 3 (sem `host`) continua valendo para todo o resto.

Aplique tudo:

```bash
kubectl apply -f admin-deployment.yaml -f admin-service.yaml -f admin-ingress.yaml

```

Como não somos donos do domínio `meusite.com`, simulamos o navegador enviando o nome manualmente (`-H` injeta o cabeçalho `Host`):

```bash
curl localhost
curl localhost -H "Host: admin.meusite.com"

```

**Dois sites diferentes, na mesma porta 80!** O primeiro `curl` traz nossa página; o segundo, o "It works!" do Apache. É exatamente assim que um mesmo IP na internet hospeda milhares de sites — o porteiro lê o nome e encaminha.

## 🔒 5. Teoria: Onde Entrariam o SSL e o Firewall?

Não vamos configurá-los, mas agora você consegue apontar o lugar exato de cada um — **tudo no porteiro, nada no site**:

* **SSL/HTTPS:** o recurso Ingress aceita um bloco `tls:`, que aponta para um certificado guardado no cluster. O porteiro passa a atender na porta 443, **descriptografa** a conversa e fala HTTP simples com o site interno (isso se chama **terminação SSL**). Em produção, uma ferramenta chamada *cert-manager* renova certificados gratuitos (Let's Encrypt) sozinha — mais YAML, mais IaC.
* **Firewall de entrada:** o nginx Ingress aceita regras via *annotations* no YAML — por exemplo, liberar apenas certos IPs (`whitelist-source-range`) ou limitar requisições por segundo contra ataques de força bruta. De novo: declarado em arquivo, versionado, replicável.

E repare no ganho arquitetural: a aplicação **nem fica sabendo** dessas proteções. Site é site, segurança é na portaria.

## 🧠 Fechando a Teoria: o que ganhamos com essa camada a mais?

* 🔒 **Segurança (o pilar da aula):** a aplicação saiu da rua e foi para a rede interna (ClusterIP). A superfície de ataque virou **um único ponto controlado** — a porta 80 do porteiro — onde SSL e firewall teriam morada.
* 📄 **Replicável:** o porteiro inteiro (incluindo as regras de roteamento!) é YAML. O ambiente continua sendo "uma pasta de arquivos".
* 💪 **Resiliente:** o Ingress Controller também é gerenciado pelo cluster — se o Pod do porteiro morrer, o Kubernetes recria. Teste se quiser: `kubectl delete pod -n ingress NOME_DO_POD` e veja o site continuar no ar após o renascimento.
* 🪢 **Elástico:** ⏳ ainda com `replicas: 1` em tudo. Na próxima aula (a última do módulo!), o porteiro mostra seu segundo talento: **balancear carga entre várias réplicas**.
