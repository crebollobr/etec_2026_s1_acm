# ☸️ Kubernetes — Aula 01: Do Contêiner ao Orquestrador (Primeiro Pod)

Nas últimas aulas, dominamos o Docker: criamos imagens, contêineres e até orquestramos serviços com o Docker Compose. Mas o Compose tem um limite: ele gerencia contêineres em **uma única máquina** e, se um contêiner morrer feio, ninguém o ressuscita sozinho.

Hoje começamos um novo módulo: **Kubernetes** (abreviado como **K8s** — K + 8 letras + s). Ele é o orquestrador de contêineres mais usado do mundo, criado pelo Google e hoje mantido pela comunidade (CNCF).

---

## 🧠 Teoria: Por que Kubernetes?

Imagine que o site da sua empresa roda em um contêiner Docker. Agora responda:

* O que acontece se o contêiner travar às 3h da manhã? *(Alguém precisa acordar e rodar `docker start`...)*
* O que acontece se entrar uma multidão de acessos na Black Friday? *(Alguém precisa criar mais contêineres na mão...)*
* O que acontece se o servidor físico pegar fogo? *(Alguém precisa reinstalar tudo em outra máquina...)*

O Kubernetes existe para responder essas perguntas **automaticamente**. Ele é um "gerente robô" que fica observando seus contêineres o tempo todo e corrige a realidade para bater com o que você pediu.

Neste módulo de 4 aulas, vamos construir passo a passo um ambiente profissional com 4 pilares:

| Pilar | O que significa | Aula |
| --- | --- | --- |
| 📄 **Replicável** | Infraestrutura como Código (IaC): todo o ambiente descrito em arquivos. Perdeu o servidor? Roda os arquivos de novo e tudo volta. | Aula 02 |
| 💪 **Resiliente** | Se um contêiner morre, o Kubernetes cria outro sozinho, sem intervenção humana. | Aulas 02 e 04 |
| 🪢 **Elástico** | Aumentou o movimento? Criamos réplicas. Diminuiu? Removemos. O ambiente "respira" conforme a demanda. | Aula 04 |
| 🔒 **Segurança** | Um único ponto de entrada controlado (proxy reverso), onde poderíamos pendurar SSL e firewall. | Aula 03 |

> 💡 **Guarde essa tabela.** Ao final de cada etapa das próximas aulas, vamos voltar nela e marcar: "esse passo que acabamos de dar constrói qual pilar?"

## 🏗️ 1. Instalando o Kubernetes (MicroK8s)

Instalar um cluster Kubernetes "de verdade" envolve várias máquinas e muita configuração. Para estudar, usamos o **MicroK8s**: uma distribuição leve de Kubernetes feita pela Canonical (a mesma empresa do Ubuntu) que roda em uma única máquina.

O MicroK8s é distribuído via **snap** — um formato de pacote do Ubuntu em que o programa vem com todas as suas dependências embutidas (parecido com a ideia de uma imagem Docker, só que para programas do sistema).

Primeiro, atualize a lista de pacotes e instale o suporte a snaps:

```bash
apt update
apt install -y snapd

```

Agora instale o MicroK8s:

```bash
snap install microk8s --classic

```

* **O que é o `--classic`?** Por padrão, snaps rodam "enjaulados", sem acesso total ao sistema. O MicroK8s precisa mexer em rede, processos e discos da máquina — então pedimos o modo clássico, sem jaula.

> 🛠️ **Se aparecer um erro** do tipo `too early for operation, device not yet seeded`, é porque o snap acabou de ser instalado e ainda está se organizando. Rode o comando de instalação novamente.

Aguarde o cluster ficar pronto (o comando só libera o terminal quando tudo estiver no ar):

```bash
microk8s status --wait-ready

```

Quando aparecer `microk8s is running`, parabéns: **você tem um cluster Kubernetes funcionando**. 🎉

## ⌨️ 2. Alias e Autocompletar — Trabalhando como Gente Grande

A ferramenta oficial para conversar com qualquer Kubernetes do mundo chama-se **kubectl** (lê-se "kube-control"). O MicroK8s já traz o dele embutido, mas o comando fica longo: `microk8s kubectl`.

Profissional não digita comando longo: cria um **alias** (apelido). E também não decora comando: usa o **autocompletar** do bash (aperta TAB e o terminal completa sozinho).

Rode o bloco abaixo — ele grava as configurações no `~/.bashrc` (arquivo que o bash lê toda vez que abre) e já as ativa no terminal atual:

```bash
echo "alias kubectl='microk8s kubectl'" >> ~/.bashrc
echo "source <(microk8s kubectl completion bash)" >> ~/.bashrc
echo "complete -o default -F __start_kubectl kubectl" >> ~/.bashrc
source ~/.bashrc

```

* **Linha 1:** cria o apelido — agora `kubectl` significa `microk8s kubectl`.
* **Linha 2:** carrega o script de autocompletar que o próprio kubectl gera.
* **Linha 3:** avisa o bash que o apelido `kubectl` deve usar esse autocompletar também.
* **Linha 4:** recarrega a configuração sem precisar fechar o terminal.

Teste o autocompletar: digite `kubectl get no` e aperte **TAB**. Ele deve completar para `nodes`. Confirme com Enter:

```bash
kubectl get nodes

```

Você deve ver **1 nó** (a sua máquina) com status `Ready`. Em uma empresa, esse mesmo comando listaria dezenas de servidores — e os comandos seriam **exatamente os mesmos** que você vai usar hoje.

## 📦 3. Etapa 1 — Levantando o Pod (só o pod, nada mais)

Hora do primeiro conceito-chave: no Kubernetes, a menor unidade não é o contêiner — é o **Pod**.

* Um **Pod** é uma "cápsula" que embrulha um ou mais contêineres.
* Todos os contêineres dentro do mesmo Pod compartilham o mesmo **IP** e o mesmo "localhost".
* Na prática do dia a dia, 90% dos Pods têm **um contêiner só** — pense no Pod como "o contêiner + o envelope que o Kubernetes usa para gerenciá-lo".

Vamos criar nosso primeiro Pod rodando a imagem do **nginx** (o mesmo servidor web que usamos no módulo de Docker):

```bash
kubectl run meu-nginx --image=nginx

```

* `kubectl run` → "Kubernetes, rode algo para mim"
* `meu-nginx` → o nome que escolhemos para o Pod
* `--image=nginx` → a imagem Docker que ele vai baixar do Docker Hub (a mesma de sempre!)

Veja o que aconteceu:

```bash
kubectl get pods

```

Provavelmente o status estará em `ContainerCreating` (ele está baixando a imagem, igual ao `docker pull`). Rode o comando de novo até aparecer `Running`.

Agora peça o "raio-x" completo do Pod:

```bash
kubectl describe pod meu-nginx

```

Role a tela e observe a seção **Events** no final: ela conta a história do Pod passo a passo — *Scheduled* (decidiu onde rodar), *Pulling* (baixando a imagem), *Pulled* (baixou), *Created* e *Started*. Quando algo der errado no futuro, é **aqui** que você vai descobrir o porquê.

> 🔍 **Compare com o Docker:** `kubectl get pods` ≈ `docker ps` | `kubectl describe` ≈ `docker inspect` | `kubectl logs meu-nginx` ≈ `docker logs`. Os conceitos que você já sabe continuam valendo, só mudou o gerente.

## 🔌 4. Etapa 2 — O Pod + Porta (acessando o nginx)

Temos um nginx rodando... mas ninguém consegue acessá-lo. Por quê?

O Kubernetes cria uma **rede interna privada** para os Pods. Cada Pod ganha um IP, mas esse IP só existe **dentro** do cluster. Veja o IP do seu Pod:

```bash
kubectl get pods -o wide

```

A opção `-o wide` (saída "larga") mostra colunas extras, incluindo o **IP**. Teste o acesso por dentro da máquina (troque pelo IP que apareceu para você):

```bash
curl IP_DO_POD

```

Funcionou! Apareceu o HTML do `Welcome to nginx!`. Mas tente abrir a porta 80 no menu **Traffic Ports** do Killercoda... nada. O navegador está **fora** do cluster, e o Pod está **dentro**.

Para criar um túnel temporário entre o mundo externo e o Pod, usamos o `port-forward`:

```bash
kubectl port-forward pod/meu-nginx --address 0.0.0.0 80:80

```

* `pod/meu-nginx` → o alvo do túnel
* `--address 0.0.0.0` → aceita conexões vindas de qualquer lugar (sem isso, só aceitaria da própria máquina, e o navegador do Killercoda não entraria)
* `80:80` → porta da máquina : porta do Pod (a mesma lógica do `-p 80:80` do Docker!)

Agora sim: abra o menu (☰) → **Traffic Ports** → **80**. O nginx aparece no navegador! 🎉

> ⚠️ Repare que o terminal ficou **ocupado** segurando o túnel. Isso é normal: o `port-forward` é uma ferramenta de teste, não a forma definitiva de expor um site (a forma definitiva vem na Aula 02, com o **Service**). Para liberar o terminal, pressione **Ctrl+C** — o túnel fecha e o site some do navegador, mas o Pod continua vivo (`kubectl get pods` para confirmar).

## 📂 5. Etapa 3 — O Pod + Porta + Volume (nosso conteúdo em `/srv/www`)

O site está no ar, mas é a página padrão do nginx. Queremos **a nossa página**. E aqui vem outro conceito fundamental:

> 🧨 **Contêineres são descartáveis.** Tudo que é gravado dentro de um contêiner morre com ele. Se quisermos que o conteúdo sobreviva, ele precisa morar **fora** do contêiner — em um **volume**. (Lembra dos volumes do Docker? Mesmo conceito.)

Primeiro, vamos criar nosso conteúdo na máquina, na pasta `/srv/www` (no Linux, `/srv` é a pasta tradicional para dados **serv**idos por serviços):

```bash
mkdir -p /srv/www

```

Salve o conteúdo abaixo como `/srv/www/index.html`:

```html
<h1>🚀 Meu primeiro site no Kubernetes!</h1>
<p>Servido por um Pod, com conteudo vindo de um volume em /srv/www</p>
```

Agora precisamos de um Pod que **monte** essa pasta dentro dele. O `kubectl run` não tem uma opção simples para volumes — chegamos ao limite dos comandos "na mão". A partir daqui, descrevemos o que queremos em um **arquivo YAML** (o mesmo formato do Docker Compose!).

Apague o Pod antigo:

```bash
kubectl delete pod meu-nginx

```

Salve o conteúdo abaixo como `meu-site.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: meu-site
spec:
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 80
    volumeMounts:
    - name: conteudo
      mountPath: /usr/share/nginx/html
  volumes:
  - name: conteudo
    hostPath:
      path: /srv/www
```

Vamos ler o arquivo de cima para baixo (na Aula 02 aprofundamos cada campo, hoje é só para perder o medo):

* `kind: Pod` → "Kubernetes, o que estou descrevendo aqui é um Pod"
* `metadata.name` → o nome dele
* `spec.containers` → a lista de contêineres (no nosso caso, um nginx)
* `volumeMounts` → "dentro do contêiner, pendure o volume `conteudo` na pasta `/usr/share/nginx/html`" (que é onde o nginx busca as páginas — lembra do módulo Docker?)
* `volumes.hostPath` → "o volume `conteudo` é, na verdade, a pasta `/srv/www` da máquina"

Peça ao Kubernetes para criar o que está descrito no arquivo:

```bash
kubectl apply -f meu-site.yaml

```

Confira se está `Running` e abra o túnel de novo (repare que agora o alvo é `pod/meu-site`):

```bash
kubectl get pods
kubectl port-forward pod/meu-site --address 0.0.0.0 80:80

```

Abra a porta **80** no menu Traffic Ports: **sua página** está no ar! 🎉

### 🔁 A prova final do volume

Com o site aberto no navegador, **sem mexer no Pod**, edite o arquivo na máquina:

```bash
nano /srv/www/index.html

```

Mude o texto do `<h1>`, salve e atualize a página no navegador (**F5**). A mudança aparece **na hora** — porque o conteúdo não está dentro do contêiner, está na pasta da máquina, e o Pod só a enxerga através do volume.

## 🧠 Fechando a Teoria: o que construímos hoje?

Volte na tabela dos 4 pilares do início da aula:

* **Replicável?** Quase. A etapa 3 já nasceu como código (`meu-site.yaml`) — se a máquina morrer, basta rodar `kubectl apply` de novo. Mas as etapas 1 e 2 foram comandos manuais. Na **Aula 02**, TUDO vira arquivo: infraestrutura como código de verdade.
* **Resiliente?** Ainda não! Faça o teste: `kubectl delete pod meu-site` — o Pod morre e **ninguém o recria**. Um Pod "solto" é órfão. Na Aula 02 conheceremos o **Deployment**, o objeto que ressuscita Pods sozinho.
* **Elástico?** Ainda não — temos 1 Pod e nenhuma forma automática de virar 10. Aula 04.
* **Seguro?** Ainda não — e repare que o `port-forward` expõe o Pod diretamente, sem nenhum controle no meio. Aula 03.
