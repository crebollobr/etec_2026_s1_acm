# ☸️ Kubernetes — Aula 02: Infraestrutura como Código (Deployment em YAML)

Na aula passada, instalamos o MicroK8s e subimos nosso primeiro Pod. Mas terminamos com uma descoberta incômoda: se alguém apagar o Pod, **ninguém o recria**. E boa parte do que fizemos foi na base de comandos digitados — se a máquina sumir, nosso trabalho some junto.

Hoje resolvemos os dois problemas de uma vez com o objeto mais importante do Kubernetes no dia a dia: o **Deployment**.

---

## 🧠 Teoria: Imperativo vs. Declarativo

Existem duas formas de mandar em computadores:

* **Imperativa** — você dá ordens, uma por uma: "crie um pod", "abra a porta", "monte o volume". Foi o que fizemos na Aula 01 com `kubectl run`. Funciona, mas as ordens se perdem: daqui a 6 meses, ninguém lembra a sequência exata de comandos que construiu o ambiente.
* **Declarativa** — você descreve **o estado final desejado** em um arquivo e entrega para o Kubernetes: "eu quero 1 site nginx, na porta 80, com este conteúdo". O Kubernetes compara o desejo com a realidade e **faz o que for preciso** para igualar os dois.

A forma declarativa tem um nome famoso no mercado: **Infraestrutura como Código** (IaC — *Infrastructure as Code*). É o pilar **Replicável** da nossa tabela:

> 📄 Se toda a infraestrutura está descrita em arquivos, então a infraestrutura pode ser **versionada no Git**, **revisada** como código e **recriada do zero em qualquer lugar** com um único comando. O servidor pegou fogo? `kubectl apply -f .` em outra máquina e o ambiente renasce idêntico.

E tem um efeito colateral poderoso: como o Kubernetes vive comparando "desejo × realidade", se um Pod morrer, a realidade fica diferente do desejo — e ele **corrige sozinho**, criando outro. Isso é o pilar **Resiliente**. Hoje veremos os dois funcionando.

## 📜 1. Etapa 1 — O Deployment Mínimo

Um **Deployment** é um objeto que diz ao Kubernetes: *"mantenha sempre N cópias deste Pod rodando, aconteça o que acontecer"*. Ele é o "contrato de trabalho" do nosso site.

Crie uma pasta para o projeto desta aula:

```bash
mkdir -p /root/projeto-site && cd /root/projeto-site

```

Salve o conteúdo abaixo como `deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: meu-site
spec:
  replicas: 1
  selector:
    matchLabels:
      app: meu-site
  template:
    metadata:
      labels:
        app: meu-site
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80
```

Esse arquivo é o coração da aula. Vamos dissecá-lo bloco por bloco:

* `apiVersion: apps/v1` → cada tipo de objeto pertence a um "departamento" da API do Kubernetes. Deployments moram no `apps/v1`. (O Pod da aula passada era do `v1` básico.)
* `kind: Deployment` → o tipo de objeto que estamos declarando.
* `metadata.name` → o nome do Deployment.
* `spec.replicas: 1` → **quantas cópias** do Pod queremos. Hoje, 1. Na Aula 04, esse numerozinho vai ser a estrela do show.
* `spec.selector.matchLabels` → o Deployment precisa saber **quais Pods são dele**. Ele não usa nomes: usa **labels** (etiquetas). Aqui dizemos: "todo Pod com a etiqueta `app: meu-site` é meu".
* `spec.template` → o **molde** do Pod. Tudo daqui para baixo é a descrição do Pod que será carimbado quantas vezes for preciso. Repare que dentro do molde existe `metadata.labels` com a **mesma etiqueta** do selector — é assim que o carimbo e o dono se encontram. *(Etiqueta diferente = erro na hora do apply.)*
* `template.spec.containers` → exatamente o que você já viu na Aula 01: imagem e porta do contêiner.

Entregue o desejo ao Kubernetes:

```bash
kubectl apply -f deployment.yaml

```

E agora veja a hierarquia completa que nasceu:

```bash
kubectl get deployments
kubectl get replicasets
kubectl get pods

```

Apareceram **três** coisas! A cadeia de comando é:

```
Deployment (o contrato: "quero 1 réplica deste molde")
   └── ReplicaSet (o capataz: conta os Pods e mantém o número certo)
          └── Pod (o trabalhador: meu-site-7d4b9c-xxxxx)
```

Repare no nome do Pod: `meu-site-` + códigos aleatórios. Você não escolhe mais o nome do Pod — ele virou **gado, não bicho de estimação** *(cattle, not pets — jargão real do mercado)*: se um morrer, outro nasce com outro nome e ninguém chora.

## 💪 2. Etapa 2 — A Prova da Resiliência

Na Aula 01, quando apagamos o Pod, ele morreu para sempre. Vamos repetir o crime, agora com o Deployment olhando.

Primeiro, deixe um "vigia" rodando — este comando fica observando os Pods em tempo real (`-w` = *watch*):

```bash
kubectl get pods -w

```

Abra um **segundo terminal** (botão **+** ao lado da aba do terminal no Killercoda) e mate o Pod (copie o nome exato que apareceu no `get pods`):

```bash
kubectl delete pod NOME_DO_POD_AQUI

```

Volte ao primeiro terminal e assista à cena: o Pod antigo aparece como `Terminating`... e **imediatamente** um Pod novo surge em `ContainerCreating` → `Running`, com outro nome.

**Ninguém digitou nada para consertar.** O ReplicaSet contou os Pods, viu `0` onde deveria haver `1`, e corrigiu. Esse ciclo eterno de *observar → comparar → corrigir* chama-se **loop de reconciliação**, e é ele que entrega o pilar **💪 Resiliente**: o contêiner pode travar às 3h da manhã — o "gerente robô" não dorme.

Pressione **Ctrl+C** no vigia para liberar o terminal.

## 📂 3. Etapa 3 — Declarando Também o Conteúdo (volume no YAML)

Nosso Deployment sobe o nginx padrão. Vamos declarar também o volume com a nossa página, como na Aula 01 — só que agora **dentro do molde**.

Crie o conteúdo na máquina:

```bash
mkdir -p /srv/www

```

Salve o conteúdo abaixo como `/srv/www/index.html`:

```html
<h1>📄 Site declarado em YAML!</h1>
<p>Se este servidor morrer, o Kubernetes recria. Se o datacenter sumir, o YAML recria.</p>
```

Agora **edite** o `deployment.yaml` (não crie outro arquivo — em IaC, evoluímos o mesmo código). Salve o conteúdo abaixo como `deployment.yaml`, substituindo o anterior:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: meu-site
spec:
  replicas: 1
  selector:
    matchLabels:
      app: meu-site
  template:
    metadata:
      labels:
        app: meu-site
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80
        volumeMounts:
        - name: conteudo
          mountPath: /usr/share/nginx/html
      volumes:
      - name: conteudo
        hostPath:
          path: /srv/www
```

As novidades são as mesmas da Aula 01 (`volumeMounts` pendura o volume na pasta de páginas do nginx; `volumes.hostPath` aponta para `/srv/www` da máquina) — só mudou o **lugar**: agora estão dentro do `template`, então **todo Pod carimbado por esse molde** nasce com o volume montado.

Aplique a mudança:

```bash
kubectl apply -f deployment.yaml

```

Olhe rápido os Pods:

```bash
kubectl get pods

```

Repare: o Kubernetes **não consertou** o Pod antigo — ele criou um Pod novo com a configuração nova e desligou o velho. Isso se chama **rolling update** (atualização gradual) e é assim que sites grandes atualizam **sem sair do ar**: os Pods novos sobem, e só então os antigos morrem.

> 🔍 Quer ver o histórico? `kubectl rollout history deployment meu-site` mostra as "versões" do seu contrato.

## 🔌 4. Etapa 4 — O Service: um Endereço Fixo para Pods Descartáveis

Falta um detalhe importante. Acabamos de ver que Pods morrem e renascem **com outro nome e outro IP**. Então como alguém encontra o site de forma confiável, se o alvo vive mudando de endereço?

A resposta é o **Service**: um objeto que cria um **endereço fixo e estável** na frente dos Pods. Ele encontra os Pods do mesmo jeito que o Deployment: pela **etiqueta** (`app: meu-site`). Pod morreu e renasceu com outro IP? O Service o encontra de novo, sozinho.

Salve o conteúdo abaixo como `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: meu-site-service
spec:
  type: ClusterIP
  selector:
    app: meu-site
  ports:
  - port: 80
    targetPort: 80
```

Dissecando:

* `kind: Service` → o tipo de objeto.
* `type: ClusterIP` → o tipo padrão de Service: cria um **IP fixo interno do cluster**. Esse IP só funciona dentro da máquina — e é proposital: a aplicação fica em "rede interna", invisível para a rua.
* `selector: app: meu-site` → "meu alvo são os Pods com esta etiqueta". *(A mesma etiqueta do Deployment — etiquetas são a cola que une tudo no Kubernetes.)*
* `port: 80` → a porta em que o Service atende.
* `targetPort: 80` → a porta do contêiner para onde ele entrega o tráfego.

Aplique e veja o endereço fixo que nasceu:

```bash
kubectl apply -f service.yaml
kubectl get services

```

Anote o `CLUSTER-IP` do `meu-site-service` e teste no terminal (troque pelo IP que apareceu para você):

```bash
curl IP_DO_SERVICE

```

### 🎯 A prova do endereço fixo

Mate o Pod de novo (`kubectl delete pod NOME_DO_POD`), espere o substituto nascer (`kubectl get pods`) e rode **o mesmo `curl` de antes**, no mesmo IP do Service:

O site responde! O Pod novo tem outro nome e outro IP — mas **o endereço do Service não mudou**. É ele quem vai servir de alvo estável para tudo daqui para frente.

### 🌐 E o navegador?

O `CLUSTER-IP`, como o nome entrega, só existe **dentro do cluster** — o navegador, lá fora, não o alcança. No nosso laboratório, a única coisa que o mundo externo enxerga é a **porta 80 da máquina**. Então, por enquanto, abrimos o túnel de teste apontando para o Service:

```bash
kubectl port-forward service/meu-site-service --address 0.0.0.0 80:80

```

Abra o menu (☰) → **Traffic Ports** → **80**. Sua página declarada em YAML está no ar! 🎉

> ⚠️ O `port-forward` continua sendo uma ferramenta de **teste**: prende o terminal e morre junto com a sessão. A porta de entrada **oficial e definitiva** na porta 80 — do jeito que as empresas fazem — é o assunto da Aula 03. Pressione **Ctrl+C** quando terminar de olhar.

## 🧠 Fechando a Teoria: o Teste do Datacenter em Chamas

Olhe para a pasta do projeto:

```bash
ls /root/projeto-site

```

Dois arquivos: `deployment.yaml` e `service.yaml`. **Isso é o seu datacenter inteiro.** A prova:

1. Destrua tudo: `kubectl delete -f deployment.yaml -f service.yaml`
2. Confira o estrago: `kubectl get pods` → nada.
3. Renascimento: `kubectl apply -f deployment.yaml -f service.yaml`
4. `kubectl get services` → pegue o novo `CLUSTER-IP` → `curl IP_DO_SERVICE` → o site voltou, idêntico.

> 🔍 Repare: ao recriar, o `CLUSTER-IP` veio **diferente**. E ninguém sofre com isso — porque, dentro do cluster, os componentes se acham pelo **nome** do Service, não pelo IP (é o DNS interno do Kubernetes, que veremos em ação na Aula 03).

Atualizando nossa tabela de pilares:

* 📄 **Replicável** ✅ — todo o ambiente em arquivos versionáveis. Esses YAML poderiam estar num repositório Git da empresa.
* 💪 **Resiliente** ✅ — o loop de reconciliação recria Pods mortos sozinho, e o Service os reencontra.
* 🪢 **Elástico** ⏳ — viu o `replicas: 1`? Aula 04.
* 🔒 **Segurança** ⏳ — o site está em rede interna (bom!), mas o acesso externo ainda é um túnel manual de teste. A porta de entrada profissional — o proxy reverso, que no Kubernetes se chama **Ingress** — é a próxima aula.
