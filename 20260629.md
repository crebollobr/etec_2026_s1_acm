# ☸️ Kubernetes — Aula 04: Elasticidade (Escalando com Réplicas)

Chegamos à última aula do módulo de Kubernetes — e ao pilar que faltava na nossa tabela: a **Elasticidade**.

Até agora, todos os nossos Deployments tinham um detalhe discreto: `replicas: 1`. Hoje, esse numerozinho vira o protagonista. Vamos transformar 1 servidor em vários com **uma linha de YAML**, ver o porteiro (Ingress) distribuindo o tráfego entre eles ao vivo, e ainda derrubar servidores no meio do caminho para provar que ninguém percebe.

---

## 🧠 Teoria: Escalabilidade e Elasticidade

Dois termos que caem em toda prova e toda entrevista:

* **Escalabilidade** é a **capacidade de crescer**. Um sistema escalável aguenta mais carga se você der mais recursos a ele. Existem duas direções:
    * **Escala vertical (scale up):** trocar a máquina por uma **mais forte** — mais CPU, mais RAM. É simples, mas tem teto (não existe servidor infinito) e geralmente exige desligar para trocar.
    * **Escala horizontal (scale out):** em vez de uma máquina mais forte, **mais máquinas iguais** dividindo o trabalho. Não tem teto prático — é assim que Google, Netflix e Mercado Livre funcionam. Mas exige algo na frente distribuindo o trabalho... um **balanceador de carga** (olá, porteiro da aula passada! 👋).
* **Elasticidade** é a escalabilidade **com vai-e-volta**: crescer quando a demanda sobe **e encolher quando ela desce**, idealmente sozinho. Black Friday chegou? 10 réplicas. Terça de madrugada? 2 réplicas — e você para de pagar pelas outras 8. Na nuvem, onde se paga por hora de máquina, elasticidade é literalmente dinheiro.

No Kubernetes, a unidade de escala horizontal é o **Pod**: como nossos Pods são descartáveis e idênticos (nascem todos do mesmo `template` do Deployment), criar mais 9 é trivial. O **Service** mantém a lista atualizada de quem está vivo, e o **Ingress** — que já escuta na porta 80 da máquina — distribui as requisições entre todos da lista.

## 🏗️ 1. Etapa 1 — Um Site que Diz Quem Ele É

Para **enxergar** o balanceamento de carga, precisamos de um truque: cada réplica vai exibir **o próprio nome** na página. Assim, quando o tráfego pular de réplica em réplica, veremos os nomes mudando.

Como fazer cada Pod ter uma página diferente, se todos nascem do mesmo molde? Usando uma variável que existe dentro de todo contêiner: o **$HOSTNAME**, que dentro de um Pod é **o nome do próprio Pod**. Vamos sobrescrever o comando de inicialização do nginx para, antes de subir, gravar uma página com esse nome.

Crie a pasta do projeto:

```bash
mkdir -p /root/projeto-elastico && cd /root/projeto-elastico

```

Salve o conteúdo abaixo como `deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: site-elastico
spec:
  replicas: 1
  selector:
    matchLabels:
      app: site-elastico
  template:
    metadata:
      labels:
        app: site-elastico
    spec:
      containers:
      - name: nginx
        image: nginx
        command: ["/bin/sh", "-c"]
        args:
          - echo "<h1>🪢 Eu sou o pod $HOSTNAME</h1>" > /usr/share/nginx/html/index.html && nginx -g 'daemon off;'
        ports:
        - containerPort: 80
```

A estrutura você já conhece de cor. As novidades:

* `command: ["/bin/sh", "-c"]` → substitui o comando de inicialização da imagem (o `CMD` do Dockerfile, lembra?) por um shell.
* `args` → o que o shell executa: **primeiro** grava o `index.html` com o nome do Pod, **depois** sobe o nginx (`daemon off;` mantém o nginx em primeiro plano — em contêiner, o processo principal não pode "ir para o fundo", senão o contêiner acha que acabou e morre).

O Service interno (o "cadastro" dos Pods vivos). Salve o conteúdo abaixo como `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: site-elastico-service
spec:
  type: ClusterIP
  selector:
    app: site-elastico
  ports:
  - port: 80
    targetPort: 80
```

E a ordem do porteiro, como na aula passada. Salve o conteúdo abaixo como `ingress.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: entrada-elastica
spec:
  ingressClassName: public
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: site-elastico-service
            port:
              number: 80
```

Aplique tudo e teste pela porta 80 da máquina:

```bash
kubectl apply -f deployment.yaml -f service.yaml -f ingress.yaml
kubectl get pods
curl localhost

```

A resposta diz o nome do (único) Pod: `Eu sou o pod site-elastico-xxxx-yyyy`. Rode o `curl` mais vezes: sempre o mesmo nome — claro, só existe um.

## 🪢 2. Etapa 2 — Escalando: de 1 para 5 com Uma Linha

Imagine: seu site saiu no Jornal Nacional e o acesso vai explodir. Em um datacenter tradicional, isso seria comprar servidor, instalar sistema, configurar tudo... semanas. No Kubernetes, é **editar um número**.

Abra o `deployment.yaml` (`nano deployment.yaml`) e mude apenas:

```yaml
  replicas: 5
```

Declare o novo desejo e assista ao parto múltiplo em tempo real:

```bash
kubectl apply -f deployment.yaml
kubectl get pods -w

```

Quatro Pods novos nascendo de uma vez (`ContainerCreating` → `Running`), todos carimbados do mesmo molde. Quando os 5 estiverem `Running`, pressione **Ctrl+C**.

> 🔍 **Por que editamos o arquivo em vez de usar um comando?** Existe o atalho imperativo `kubectl scale deployment site-elastico --replicas=5` — e ele funciona. Mas pense: o comando se perde, o arquivo fica. Se amanhã alguém reaplicar o YAML com `replicas: 1`, a escala feita "na mão" desaparece. Em Infraestrutura como Código, **o arquivo é a verdade** — comandos imperativos são para emergências e testes.

E o Service? Ele já cadastrou os 5 sozinho. Veja a lista de "alvos" dele:

```bash
kubectl get endpoints site-elastico-service

```

Cinco IPs! Todos os Pods com a etiqueta `app: site-elastico` entraram automaticamente na lista — e é essa lista que o porteiro consulta. **Nenhuma configuração extra.**

## 🎯 3. Etapa 3 — Vendo o Balanceamento de Carga ao Vivo

Agora a cena mais bonita do módulo. Dispare 10 requisições seguidas para a porta 80:

```bash
for i in $(seq 1 10); do curl -s localhost; done

```

Olhe os nomes: **as respostas vêm de Pods diferentes!** Lembra que na aula passada dissemos que o proxy reverso também balanceia carga? Ei-lo trabalhando: o Ingress recebe cada requisição na porta 80 e a entrega para uma réplica diferente da lista. Isso é **balanceamento de carga**: 5 servidores dividindo o trabalho atrás de um único endereço.

Abra também no navegador (menu ☰ → **Traffic Ports** → botão **80**) e atualize a página algumas vezes (**F5**) para ver os nomes alternando.

> 💡 **As três peças, cada uma no seu papel:** o **Deployment** garante que existam 5 réplicas; o **Service** mantém o cadastro de quem está vivo; o **Ingress** atende na porta 80 e distribui. Arquitetura completa — e 100% declarada em YAML.

## 💪 4. Etapa 4 — Resiliência + Elasticidade: o Teste do Caos

As empresas grandes fazem o chamado *chaos engineering*: derrubar pedaços do sistema **de propósito** para provar que ele aguenta. Vamos fazer nossa versão.

Deixe um vigia disparando requisições sem parar:

```bash
while true; do curl -s localhost; sleep 1; done

```

Abra um **segundo terminal** (botão **+**) e mate um Pod qualquer (copie um nome do `kubectl get pods`):

```bash
kubectl delete pod NOME_DE_UM_POD_AQUI

```

Volte ao primeiro terminal e observe: **o fluxo de respostas não parou em momento nenhum.** O Pod morto saiu do cadastro do Service na hora, as outras 4 réplicas seguraram o tráfego, e o ReplicaSet já está dando à luz um substituto (confira no segundo terminal com `kubectl get pods` — repare no Pod novinho com `AGE` recente).

Réplicas + recriação automática + balanceamento = **um sistema onde servidores morrem e o usuário nunca fica sem resposta.**

Pressione **Ctrl+C** no vigia para liberar o terminal.

E o caminho de volta da elasticidade? Edite o `deployment.yaml` para `replicas: 2`, aplique e veja 3 Pods serem encerrados (`Terminating`). Demanda caiu, infraestrutura encolheu, dinheiro economizado.

## 🤖 5. Etapa 5 (Bônus) — Elasticidade Automática: o HPA

Até aqui, **nós** decidimos o número de réplicas. Mas a elasticidade de verdade é **automática**: o sistema mede o uso de CPU e decide sozinho. No Kubernetes, quem faz isso é o **HPA** (*Horizontal Pod Autoscaler*).

> ⚠️ Esta etapa é um experimento guiado: o playground é pequeno e o HPA reage em ciclos de verificação — pode não dar tempo de ver o show completo. Vale a tentativa!

O HPA precisa de um "medidor" instalado no cluster:

```bash
microk8s enable metrics-server

```

E precisa que o Deployment declare quanto de CPU cada Pod **pede** (senão "50% de uso" não significa nada). Edite o `deployment.yaml` e adicione, dentro do contêiner (mesmo nível de `image:`):

```yaml
        resources:
          requests:
            cpu: 100m
```

*(`100m` = 100 milicores = 10% de um núcleo de CPU.)* Volte também o `replicas:` para `1` e aplique:

```bash
kubectl apply -f deployment.yaml

```

Agora crie o contrato de elasticidade: "mantenha o uso de CPU em torno de 50%; pode variar de 1 a 5 réplicas":

```bash
kubectl autoscale deployment site-elastico --cpu-percent=50 --min=1 --max=5

```

Gere tráfego pesado com um Pod "atacante" (repare: ele ataca o Service **pelo nome**, via DNS interno) e observe o HPA reagir:

```bash
kubectl run gerador-carga --image=busybox --restart=Never -- /bin/sh -c "while true; do wget -q -O- http://site-elastico-service; done"
kubectl get hpa -w

```

Acompanhe a coluna `TARGETS` (uso atual/alvo) e `REPLICAS`: quando o uso passar de 50%, o número de réplicas sobe sozinho. Pare o vigia com **Ctrl+C**, encerre o atacante (`kubectl delete pod gerador-carga`) e, após alguns ciclos de verificação, o HPA encolhe as réplicas de volta. **Isso é elasticidade automática** — a infraestrutura respirando conforme a demanda, sem humano no circuito.

| Pilar | Como conquistamos | Aula |

Você saiu de "rodar um contêiner" para **arquitetar um ambiente que se replica, se cura e se adapta**. Esse conjunto de práticas tem nome no mercado: **Cloud Native** — e é exatamente assim que operam as infraestruturas modernas que você vai encontrar por aí.
